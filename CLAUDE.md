# CLAUDE.md

## Project

A Windows app that turns a webcam into a mouse pointer using hand tracking. The index fingertip moves the cursor, a pinch clicks. Built in C++ as a portfolio project, so code quality, clear design decisions, and measurable performance matter as much as features.

The developer is learning this stack. When you make a non-obvious design choice, explain it briefly in your reply and in a short code comment.

## Solution layout

- **Engine**: Win32 C++ app (starts as a console app, becomes a tray app later). Owns the camera, hand tracking, smoothing, gestures, and cursor input. Keeps running when the Control Panel is closed.
- **ControlPanel**: WinUI 3 app in C++/WinRT (packaged). Settings UI (sensitivity, smoothing, active-box size, pinch threshold, scaling), plus a camera view that draws the preview the Engine sends. Never runs tracking code or opens the camera.
- **Shared**: C++ static library. Settings struct, IPC message format, and pure logic (filters, gesture detection, coordinate mapping) so it can be unit tested.

**Current state:** solution `SeenTax.slnx` holds `Engine\` (a Windows app without a console or window of its own; a tray icon whose menu has "Hand tracking" on/off and Exit), `Shared\` (static library) and, at the root, the WinUI 3 project `SeenTax.vcxproj`: the ControlPanel. It is the toolbar window (hand tracking on/off, pointer speed, camera view under the toolbar in `CameraView.xaml`) and its settings panel (poses for the mouse actions, camera, CPU/GPU, recenter, camera status and fps). The pointer is always absolute: the hand's place in the active area is the cursor's place on the screen. Either hand can point, with no left/right setting: the Engine keeps following the hand it tracks, and once that hand is lost it takes only a hand near where it was, or any hand after `kSwitchHandsAfter` (0.5 s), so a second hand in view never takes over (`Search` in `Engine\HandTracker.cpp`). A new hand is followed only once the hand check passes (`HandVerifier` in `Shared\HandCheck.h`): the landmark model must be at least `kSurePresence` (0.7) sure for `kConfirmFrames` (3) frames in a row, with the hand's square staying in about the same place and size; the hand that was just followed needs one such frame. A followed hand is dropped below `kKeepPresence` (0.5), after `kWeakTooLong` (1 s) without reaching 0.7, or when its square is smaller than `kMinSquare` (0.10 of the picture height), larger than `kMaxSquare` (3.0) or jumps between two frames. The status line counts failed hand checks. These limits are first guesses. Which hand that is comes from its position, not from the landmark model's left/right guess, which flips when the palm turns. When the Engine takes a new hand that way (after a switch, a rest or tracking off and on, but not the first hand after it starts), it moves the active area so the hand's spot maps to where the cursor is now, so the pointer continues instead of jumping (`PointerCenter` in `Engine\TrackingLoop.cpp`, `AreaCenterFor` in `Shared\CursorMapping.cpp`); Recenter puts the area back. A pointer speed change does the same, so the cursor stays where it is and only later movement uses the new speed; the toolbar's slider sends the speed once it has stopped changing for `kSpeedSettleTime` (0.3 s), not at every step (`OnSpeedChanged` in `MainWindow.xaml.cpp`). The area has to stay inside the camera picture, so at low speeds the pointer can still move when the area is placed again. Gesture limits are in hand units, shares of the camera picture (`kDragDistance`, `kMaxPinchStartSpeed` and the prediction speeds in `Shared\PointerController.h`, scaled by `PointerSample::activeAreaSize`), so the same hand movement gives the same result at every pointer speed. Precision scaling (`PrecisionPointer` in `Shared\CursorMapping.h`): while the smoothed hand moves slower than `kPreciseBelow` (0.2 desktop widths per second) the pointer moves less than the hand, and faster moves win the difference back over about `kCatchUpDistance` (0.1 desktop widths) of travel, so hand and pointer stay lined up. The status line's jitter shows raw -> smoothed -> pointer. The camera view shows a distance hint (Move closer / Good distance / Move back) from the size of the hand's tracking square as a share of the picture height, smoothed over 0.5 s: below `kTooFarBelow` (0.30) too far, above `kTooCloseAbove` (0.70) too close (`DistanceOf` in `Shared\HandRegion.h`; first guesses, the status line logs the value for tuning). The window has only a close button, opens at the bottom-left of the screen, is as wide as the toolbar's contents (measured once the toolbar has loaded), and grows upward for the camera view while it's in the lower half of the screen. Besides the mouse actions, one action controls Windows: Close app, always a fist closed and opened within `kMaxFistTapDuration` (0.5 s), sends `SC_CLOSE` to the focused window, the same as Alt+F4, skipping the desktop, the taskbar and the Engine's own windows. It isn't in the settings panel; `Normalized` in `Shared\Settings.h` keeps it on the fist. There is no fist hold and no drag and drop. Screenshot is the two-hand frame gesture, also not in the settings: each hand makes an L (thumb out, index straight, the other three fingers curled; `MakesL` in `Shared\FrameGesture.h`), the two Ls sit at opposite corners and open toward each other (`FormFrame`), and held for `FrameDetector::kHoldFor` (0.5 s) it presses Win+PrtScn once (`TakeScreenshot` in `Engine\SystemActions.cpp`; Windows saves the whole screen to Pictures\Screenshots) and the tray shows "Screenshot taken". The pointer stays still while the frame is held. The second hand is only looked for while the tracked hand makes an L (`LookForOtherHand` in `Engine\HandTracker.cpp`: the palm detector at most every `kOtherHandSearchEvery`, 0.2 s, then the landmark model on that hand each frame); it never moves the pointer. The L and frame limits are first guesses; the status line logs the L values for tuning. Default gestures (`kDefaultPoses` in `Shared\Settings.h`): index tap = left click, middle tap = right click, double click off, index hold = Select / move (press and hold: select text, move or resize windows), middle hold = scroll, fist = close app. Each action offers only its kind of pose (`Allows` in `Shared\Settings.h`): left and right click a tap, double click a double tap, Select / move and scroll a hold; a saved choice that breaks this is turned off. The fist is a third trigger next to the index and middle pinches (`Shared\Fist.h`, `Trigger` in `Shared\PointerController.h`) and wins over a pinch that starts at the same time. Scroll freezes the pointer and turns the mouse wheel in the window under it as the hand moves up or down while the pinch is held: up scrolls up, one notch per 1/40 of the camera picture's height (`StartScroll` in `Shared\PointerController.cpp`). Once a pinch has become a drag or a scroll, it ends only when the pinch value passes the fixed release line (`PinchDetector::kReleaseAbove`), not when it rises a little above its tightest point as a tap does, and it survives up to `kLostHandGrace` (0.2 s) of lost tracking (`StillHeld` and `HandGone` in `Shared\PointerController.cpp`). Every control goes to the Engine, which applies it live. While no Engine is connected, the toolbar says "Engine not running" and the controls are off. The ControlPanel's MSIX package also carries the Engine (`Engine.exe`, its three Windows ML DLLs and `models\` at the package root, listed as `AppxPackagePayload` items in `SeenTax.vcxproj`), and the ControlPanel starts it when it opens and no Engine is running (`StartEngine` in `EngineConnection.cpp`). Models (both checked against their expected inputs/outputs at startup): landmark model `models\handpose_estimation_mediapipe_2023feb.onnx` (hand_landmark_lite) and palm detector `models\palm_detection_mediapipe_2023feb.onnx` (palm_detection_lite; input `input_1` float32 [1,192,192,3], outputs [1,2016,18] boxes and [1,2016,1] scores). Test photos: `testdata\hand.jpg` (upright) and `testdata\hand_tilted.jpg` (the same photo turned 40° clockwise).

Live tracking in the Engine is split by job: `LiveTracking.cpp` (start-up, the message loop, applying settings), `MessageWindow` (the hidden window other threads post to, and the hotkey), `TrackingLoop` (one camera frame at a time: tracker, recalibration, pointer, preview, status), `HandPointer` (smoothing, pinch, fist and frame detection, giving a `PointerSample`), `GestureLog` (the pinch, fist and frame log lines), `TrackingStatus` (the once-a-second status line) and `PreviewFrame` (the camera view message).

Engine and ControlPanel communicate over named pipes that the Engine serves (claiming them at startup keeps a second Engine from running) and the ControlPanel connects to: `\\.\pipe\SeenTax.Engine.<session id>` for control, one JSON object per message (`Shared\ControlMessages.h`): the ControlPanel sends changes (`EngineRequest`, numbered with `seq`), and the Engine sends its `EngineState` (settings, cameras, camera status, fps, recalibration, the last `seq` it applied) when the ControlPanel connects, after each request and whenever something changes. There is also `\\.\pipe\SeenTax.Preview.<session id>`, connected only while the camera view is open, one binary message per camera frame: a `PreviewHeader` (hand points, pinch value, last gesture, ...) and a picture of at most 320x240 BGRA (`Shared\PreviewMessage.h`). Settings persist as JSON in `%LOCALAPPDATA%\SeenTax\settings.json` (`Shared\Settings.h`). Only the Engine reads and writes that file. Inside a package, Windows would move new AppData files into a private package folder, so the manifest excludes `%LOCALAPPDATA%\SeenTax` from that (flexible virtualization, which needs the `unvirtualizedResources` capability): the packaged Engine and the one Visual Studio starts use the same folder.

## Tech stack (fixed, don't change without asking)

- C++20, x64 only, Windows 11 and later: `MinVersion="10.0.22000.0"` on both `TargetDeviceFamily` lines of `Package.appxmanifest` and `WindowsTargetPlatformMinVersion` in `SeenTax.vcxproj`, which the build writes into the `Windows.Universal` line (with the installed SDK as its `MaxVersionTested`). Engine and Shared have no minimum of their own; inside the package they follow the package's.
- Windows ML: its ONNX Runtime with the CPU and DirectML execution providers (`Microsoft.Windows.AI.MachineLearning` NuGet, self-contained in the Engine). The Engine's "Run hand tracking on" setting picks the device: `cpu`, `gpu` (a discrete GPU first) or `auto` (Windows' preferred GPU if it is discrete, otherwise the CPU).
- Models: MediaPipe palm detection and hand landmark models, converted to ONNX. Only the `.onnx` files are used.
- Camera: `Windows.Media.Capture` + `MediaFrameReader` via C++/WinRT.
- Cursor: `SendInput` with `MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_VIRTUALDESK`, coordinates normalized to 0–65535. Process is per-monitor DPI aware (v2).
- JSON: `Windows.Data.Json` (no third-party JSON library).
- Image loading for tests: `stb_image.h` (single header, test code only).

## Do not

- Add OpenCV, the MediaPipe framework, Python, or any other dependency. Ask first if something seems necessary.
- Install NuGet packages. The developer does that in Visual Studio; tell them which package is needed.
- Use raw COM (`AddRef`, `Release`, `QueryInterface`) where C++/WinRT covers the API.
- Guess a model's input/output names, shape, layout (NHWC vs NCHW), or value range. Ask the developer to check the model in Netron and confirm.
- Jump ahead to a later milestone.

## Code style

- RAII everywhere; no raw `new`/`delete`.
- `std::span` for buffers, `std::jthread` for threads, `co_await` for WinRT async calls.
- Keep pure logic (One Euro filter, pinch detection, landmark decoding, coordinate mapping) free of I/O and Windows APIs, in Shared, so it can be unit tested.
- Small, named functions over long ones.

## Building

MSBuild is not on PATH in Claude's shell, so call it by full path (the developer can use the Developer PowerShell for Visual Studio instead):

```powershell
$msbuild = "C:\Program Files\Microsoft Visual Studio\18\Community\MSBuild\Current\Bin\MSBuild.exe"
& $msbuild SeenTax.slnx -t:restore -p:RestorePackagesConfig=true   # restores packages already in packages.config; never adds new ones
& $msbuild SeenTax.slnx -p:Configuration=Debug -p:Platform=x64 -m -v:minimal
```

Build after each change and fix errors before reporting back. You can build ControlPanel but not run it (packaged apps are deployed and launched from Visual Studio by the developer).

The downloadable package is made by the developer in Visual Studio: SeenTax project > Package and Publish > Create App Packages > Sideloading, Release x64, signed with a certificate whose subject matches the manifest's `Publisher="CN=Parsa"`. Signing and installing are the developer's steps. To check what goes into a package without signing it, Claude can add `-p:GenerateAppxPackageOnBuild=true -p:AppxPackageSigningEnabled=false -p:UapAppxPackageBuildMode=SideloadOnly -p:AppxBundle=Never -p:AppxPackageDir=<scratchpad folder>\` to a Release build and list the `.msix` (a zip).

Running Engine (from the `Engine` folder, which is Visual Studio's working directory; the models load from `models\` next to `Engine.exe`, where the build copies them): no arguments tracks the hand live and moves the cursor; `--no-cursor` never touches the mouse, scrolls, takes a screenshot or closes a window (it only logs them); `--seconds N` stops after N seconds; `--photo FILE` runs the photo regression test (use both test photos) on the CPU, or on another device with `--device gpu|auto`; `--benchmark FILE` times both models on cpu, gpu and auto (use the Release build, and note that a laptop on battery saver gives slower CPU numbers and makes Windows prefer the integrated GPU). Live tracking has no window: the camera picture with the hand points, pinch bar and last gesture shows in the ControlPanel's camera view, and the Engine's tray icon (click it → Exit) quits it. Live runs use the saved settings: with hand tracking off, the camera doesn't start. **When Claude runs Engine live, always pass `--no-cursor`**: moving the real cursor is for the developer's own tests. Live tests need the Release build; Debug is ~10x slower.

The Engine has no console. Everything it reports goes to `%LOCALAPPDATA%\SeenTax\Engine.log` (the run before is kept as `Engine.previous.log`) and, under the debugger, to Visual Studio's Output window. If live tracking can't start it also shows a message box. Because it is a Windows app, the shell doesn't wait for it: Claude runs it with `Start-Process -WorkingDirectory Engine -PassThru`, waits with a timeout (a message box would otherwise block), and then reads the log.

## Milestones

Work on one milestone at a time. Each must end with something that works.

0. **Photo test.** Console program: load the hand landmark model and one photo of a hand, run inference, print the 21 landmarks. **Done.**
1. **Palm detection on photos.** Run the palm detector (`models\palm_detection_mediapipe_2023feb.onnx`) on the photo, decode its anchors and remove overlapping detections (in Shared), turn the best palm into a rotated square around the whole hand, run the landmark model on that square, and map the 21 points back to the photo. Must work on an upright and a tilted photo. **Done.**
2. **Live tracking.** Webcam frames via `MediaFrameReader`. The palm detector finds the hand on the first frame and whenever the hand is lost; otherwise each frame is cropped from the previous landmarks. Index fingertip moves the cursor. **Done.**
3. **Usable pointer.** One Euro filter smoothing. Pinch gestures on one hand, like Apple Watch (pinch = thumb-index distance normalized by hand size): tap = left click, double tap = right click, pinch and hold (or pinch and move) = left button held down until you let go (drag and drop, resizing windows, dragging scrollbars), and nothing else clicks; the cursor stays frozen from pinch start until the gesture is decided. Cursor thread runs at monitor refresh rate with prediction between camera frames. Record the demo here. **Done.**
4. **Control Panel.** A small, Magnifier-style floating toolbar (WinUI 3): an on/off switch, a slider (what it controls is not decided yet), and a settings (gear) button that opens the rest: hand (left/right), hand pose, recalibrate the mouse, camera picker, absolute/relative mode, live FPS display. JSON settings, live updates over the named pipe. Engine gets a tray icon with an on/off switch, so tracking can be turned off without opening the Control Panel.
5. **Polish.** Windows ML with GPU execution provider and a CPU/GPU/Auto setting, latency benchmarks, unit tests, README with numbers.

**Current milestone: 5**
